# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## CRITICAL: Session Management

**NEVER kill Claude processes!** When diagnosing hangs or performance issues:

1. **Check my own PID**: `echo $$` - This is MY process ID
2. **Never run**: `kill` on any `claude` process - that's ME!
3. **Never run**: `ps aux | grep claude` and kill those PIDs
4. **Instead**: Read log files, check task state, examine output files
5. **If truly stuck**: Ask the user to restart the pipeline, don't self-terminate

When investigating Task 002 or other hanging tasks:
- Read `.claude/task-state.json` to see active state
- Read output files directly with `cat` or `head`
- Check `.logs/atomic.log` for error messages
- **Do NOT kill processes** - that terminates my own session!

## Overview

ATOMIC CLAUDE is a script-controlled LLM orchestration system for deterministic software development pipelines. **The script is sovereign** - Bash controls all flow, state, and decisions. Claude is invoked only for non-deterministic tasks (analysis, generation, review) through bounded prompts.

## Core Architecture

### Control Flow

```
SCRIPT ──prompt.md──► CLAUDE ──output.json──► SCRIPT ──validation──► NEXT_STEP
  │                                              │
  ▼                                              ▼
[state.json]                                [state.json]
```

Each Claude invocation is:
- **Atomic**: Single purpose, no side effects
- **Bounded**: Explicit input (prompt.md) and output (json/md)
- **Validated**: Script checks output before proceeding
- **Stateless**: Claude sees only what the prompt provides

### Key Principles

1. **Script decides, Claude advises** - Never let LLM control workflow
2. **Bounded prompts** - Every call has a markdown file defining exactly what it does
3. **Structured output** - Parseable JSON/markdown, validated before use
4. **No context bleed** - Session terminates after task, fresh start every time
5. **Human gates are script logic** - Not "Claude please ask" but script literally waits

## LLM Invocation

All LLM calls go through `atomic_invoke()`:

```bash
atomic_invoke <prompt_file|string> <output_file> <description> [options]

Options:
  --model=<model>     sonnet|opus|haiku (default: sonnet)
  --format=json       Validate JSON output
  --timeout=<secs>    Override timeout (default: 300)
  --stdin             Append stdin content to prompt
```

### Multi-Provider Support

Provider routing is configured in `config/models.json`:

| Provider | Use Case | Fallback Chain |
|----------|----------|----------------|
| **max** | Claude subscription (primary workhorse) | max → api → ollama |
| **api** | Claude API (pay-per-token) | api → ollama |
| **ollama** | Local/airgapped (cost-free) | Tier-based model selection |

Role routing:
- `primary`: Main workhorse (PRD, code gen) → max/sonnet
- `fast`: Quick validation → ollama/llama3.2:3b or haiku
- `gardener`: Context maintenance → ollama/phi3:mini
- `heavyweight`: Complex reasoning → max/opus

### Airgapped/Offline Mode

For environments without internet:

```bash
export ATOMIC_OFFLINE_MODE=true
export ATOMIC_PREFER_LOCAL=true
export CLAUDE_PROVIDER=ollama

# Minimum pull set for 32GB+ RAM
ollama pull devstral:24b    # Primary workhorse
ollama pull llama3.2:3b     # Fast validation
ollama pull llama3.1:8b     # Fallback workhorse
```

See `docs/AIRGAPPED-MODEL-RANKING.md` for complete agent-to-model mapping.

## Task Structure

Each phase has numbered tasks (e.g., 101, 102, 103). Tasks are defined in `phases/<phase>/tasks/<task>.sh`:

```bash
task_205_prd_authoring() {
    atomic_step "PRD Authoring"

    # Gather context
    local context="..."

    # Build prompt
    cat > prompt.md << EOF
    <context>$context</context>
    Generate PRD following 15-section template...
    EOF

    # Invoke LLM
    atomic_invoke prompt.md output.md "Generate PRD" --model=opus

    # Validate output
    if [[ ! -f output.md ]]; then
        atomic_error "PRD generation failed"
        return 1
    fi
}
```

### Task State

Tasks track completion in `.claude/task-state.json`:

```bash
task_state_init "2-prd"                    # Initialize phase
task_state_should_skip "205" && return 0   # Skip if already done
task_state_complete "205" "PRD Authoring"  # Mark complete
task_state_fail "205" "Error message"      # Mark failed
```

Use `--resume-at=NNN` to skip completed tasks, `--redo` to force rerun.

## Persistent Memory

Atomic Claude persists project context across sessions using local file storage (`.state/memory/`):

### Configuration

Enable via Phase 0 setup or environment:

```bash
export ATOMIC_MEMORY_ENABLED=true
```

Or in `.outputs/0-setup/secrets.json`:

```json
{
  "memory_enabled": true
}
```

### Architecture

- **Session bootstrap**: Recalls context on `./main.sh run`
- **Task-level memory**: Each task recalls/saves based on needs
- **Phase checkpoints**: Saves summary at closeout (with approval)
- **Backtrack detection**: Warns when re-running earlier phases

Memory is stored in `.state/memory/phase-N/` with task-specific files and closeouts.

## Agent Selection

Phase 1 (Discovery) and Phase 2 (PRD) select agents from `agents/agent-inventory.csv`:

- **221 agents**: 186 expert agents + 35 pipeline agents
- **Graded**: Composite score (0-100), only Grade A (90%+) included
- **Categories**: 20 domains (backend, frontend, cloud, security, etc.)
- **Manifest**: `agents/agent-manifest.json` generated by `agents/build-manifest.sh`

Tasks call `atomic_invoke()` with agent-specific prompts to match project needs.

## Phase Audits

Each phase ends with an audit using `lib/audit.sh`:

1. **Filter by SDLC phase**: `AUDIT-INVENTORY.csv` has columns for each phase (discovery, prd, tasking, etc.)
2. **AI prioritizes**: From 50-200 pre-filtered audits (not all 2,186)
3. **User approves**: Review and confirm selection
4. **Execute**: Run selected audits
5. **Report**: Generate audit report in `.outputs/audits/`

Audits cover security, performance, reliability, accessibility, compliance, and more.

## Skills System

## Important Patterns

### When to Use LLM

| Category | Example | LLM? |
|----------|---------|------|
| File operations | mkdir, cp, chmod | **No** |
| Git operations | commit, push, tag | **No** |
| User input | collect name, menu | **No** |
| Validation | check file exists | **No** |
| State management | read/write JSON | **No** |
| **Analysis** | summarize docs | **Yes** |
| **Synthesis** | generate PRD | **Yes** |
| **Code generation** | write tests | **Yes** |
| **Review** | security audit | **Yes** |

~85% of tasks are deterministic. Only invoke LLM for the ~15% that truly require it.

### Context Management

Prompts should be self-contained. Gather context from:
- `.outputs/0-setup/project-config.json` - Project metadata
- `.outputs/1-discovery/selected-approach.json` - Chosen approach
- `.outputs/2-prd/prd-interview.json` - Requirements
- `docs/prd/PRD.md` - Product requirements
- `.state/memory/` - Persistent context (if enabled)

Always truncate large files with `head` or `jq` to manage token usage.

### Error Handling

Tasks return 0 on success, non-zero on failure:

```bash
task_123_example() {
    if ! some_command; then
        atomic_error "Command failed"
        return 1
    fi
    return 0
}
```

Use `set -euo pipefail` at script start for strict error handling.

## Common Workflows

### Adding a New Task

1. Create `phases/<phase>/tasks/<task_id>-<name>.sh`
2. Define function `task_<id>_<name>()`
3. Source in `phases/<phase>/run.sh`
4. Call from phase workflow

### Modifying Agent Selection

1. Edit `agents/agent-inventory.csv`
2. Run `cd agents && ./build-manifest.sh`
3. Commit both CSV and JSON

### Adding a Skill

1. Create `skills/<name>/SKILL.md`
2. Add auto-detection logic to relevant task script
3. Inject skill content into prompt via `cat skills/<name>/SKILL.md`

### Customizing Audit Selection

1. Create `initialization/audit-plan.md`
2. Set profile (minimal, standard, comprehensive)
3. Override min/max recommendations if needed
4. Run phase with audit
