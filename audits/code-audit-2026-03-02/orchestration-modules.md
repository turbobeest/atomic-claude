| 4 | orchestration/backtrack.py | A-4 Return Type Consistency | MEDIUM | `backtrack_to()` has inconsistent return values: returns `False` on EOFError (line 392), returns `None` via bare `return` on cancellation (line 400), returns `None` via bare `return` on invalid input (lines 367, 406, 421), and falls off the end with implicit `None` on success (after line 495). | 5 | orchestration/phase_runner.py | E-1 Exception Handling | MEDIUM | In the retry loop (lines 276-336), when an exception occurs on an attempt that is NOT the final attempt, the exception is caught and `last_error` is set, but `success` remains `None` (never set to `False`). On the next iteration, `attempt > 0` triggers the cooldown path. If ALL attempts raise exceptions and none is the "final" attempt check (line 333), the loop exits with `success = None`. The subsequent check `if success is False` (line 349) does NOT trigger, so the task is treated as successful and marked complete despite all attempts failing with exceptions. | 276-336, 349 | A task that raises exceptions on every attempt where `max_attempts > 1`. The exception handler at line 328-335 only sets `success = False` when `attempt == max_attempts - 1`. If `max_attempts` is 1, attempt 0 IS the last attempt and it works. But with `max_attempts >= 2`, exceptions on earlier attempts leave `success = None`. | After the retry loop, add `if success is None: success = False` or change the final-attempt check to set `success = False` unconditionally on exception. |
| 6 | orchestration/dashboard_sync.py | G-2 File Locking | MEDIUM | `_locked_file()` on Windows uses `msvcrt.locking()` with a hardcoded lock range of `2**20` (1MB) at line 63. If the file being locked is larger than 1MB, only the first 1MB is locked, leaving the rest unprotected against concurrent writes. The `errors.json` file grows unboundedly (append-only at line 436) and could exceed 1MB in long-running pipelines. More critically, `msvcrt.locking` with `LK_LOCK` locks byte ranges, not the whole file -- reads and writes beyond the locked range are unprotected. | 63, 75, 430-447 | Long-running pipeline on Windows where `errors.json` grows past 1MB due to many logged errors. Concurrent dashboard reads could see partial JSON. | Use a separate lockfile (e.g., `errors.json.lock`) with `msvcrt.locking` on byte 0, or use `win32file.LockFileEx` for whole-file locking, or use the `portalocker` library. |
| 7 | orchestration/backtrack.py | B-3 Data Integrity | MEDIUM | At line 205, `errors_file.write_text('{"errors": []}')` performs a non-atomic write to clear the error log. If the process crashes mid-write, the file could be left empty or with partial JSON. All other file writes in the backtrack module use atomic temp-file + `os.replace()` pattern (e.g., line 469-479 for state file). | 205 | Process kill signal (SIGKILL/power loss) during the `write_text` call at line 205 during backtrack cleanup. | Use the same atomic write pattern: write to temp file, then `os.replace()`. |
| 8 | orchestration/phase_runner.py | E-3 Resource Cleanup | MEDIUM | `create_phase_closeout()` at line 498-500: the `except` clause calls `os.unlink(tmp)` then `raise`. However, `os.unlink(tmp)` operates on a string path `tmp` returned by `tempfile.mkstemp()`. If `os.fdopen(fd, 'w')` at line 495 raises an exception, the file descriptor `fd` is leaked (never closed) because `os.fdopen` failed before taking ownership of it. The `except` block only unlinks the file but does not close the fd. | 493-500 | `os.fdopen(fd, 'w')` fails (e.g., due to encoding issues or permission change between mkstemp and fdopen). The file descriptor leaks. | Close `fd` in the except block before unlinking: `os.close(fd)` (guarded by a flag tracking whether fdopen succeeded). |

## Summary

**Files audited**: 10 (pipeline.py, phase_runner.py, task_display.py, task_memory.py, pre_task_validation.py, dashboard_sync.py, backtrack.py, memory_enrichment.py, retry_policy.py, team_session.py)

**Findings by severity**:
- CRITICAL: 0
- HIGH: 1
- MEDIUM: 7

**Key risk area**: `phase_runner.py` contains the highest density of findings (3 of 8), consistent with its role as the most complex module -- it orchestrates task execution with retry logic, agent roster management, skill/gravity assessment, and graph context assembly.

**Clean modules** (no MEDIUM+ findings): task_display.py, task_memory.py, pre_task_validation.py, memory_enrichment.py, retry_policy.py, team_session.py. These modules are well-structured with appropriate error handling.

**Most critical finding**: Finding #5 (phase_runner.py retry loop) can cause a task that fails on every attempt with exceptions to be incorrectly marked as successful, potentially corrupting pipeline state.
