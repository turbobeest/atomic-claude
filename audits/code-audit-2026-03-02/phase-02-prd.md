| 1 | orchestrator02.py | B-2 Path construction | HIGH | `OUTPUT_DIR` defaults to `ATOMIC_ROOT.parent / '.outputs' / '2-prd'` (line 48). When `ATOMIC_ROOT` is set via env var as a string, `Path(os.getenv(...))` works, but the default `Path.cwd()` makes `ATOMIC_ROOT.parent` point to the CWD's parent, not the project root's parent. However, the real issue: when `ATOMIC_ROOT_OUTPUT_DIR` env var is NOT set, the fallback computes `ATOMIC_ROOT.parent / '.outputs' / '2-prd'`. This places outputs inside `atomic-claude/../.outputs/` which is correct for the operational layout. But if `ATOMIC_ROOT` env var is set to a path WITHOUT a trailing component (e.g., `/`), `ATOMIC_ROOT.parent` is still `/`, creating `/.outputs/2-prd`. This is a module-level computation that cannot be overridden per-call since `run_phase_tasks` receives the already-computed `OUTPUT_DIR`. | 47-48 | `ATOMIC_ROOT` env var set to a filesystem root or unusual path; `ATOMIC_OUTPUT_DIR` not set. `OUTPUT_DIR` resolves to an unexpected location, and all phase artifacts are written there. | Validate `OUTPUT_DIR` is a reasonable path (not filesystem root) before use, or defer computation to `run_phase()` where it can be validated. |
| 2 | task_205_prd_authoring.py | D-1 Return type contract | MEDIUM | `generate_section()` calls `invoke()` (which is `invoke_llm`) and checks `if content and output_file.exists()` at line 344. The `invoke_llm` function writes the response to `output_file` itself (line 714-715 of invoke.py), then `generate_section` re-reads it from file (line 346). If `invoke_llm` raises no exception but returns an empty string, `content` is `""` (falsy), and the `else` branch returns `""`. This is correct. However, if `invoke_llm` returns a non-empty string but fails to write the file (e.g., disk full, permissions), the code falls through to `return ""` silently, losing the LLM response that was successfully generated. The response is in `content` but discarded because `output_file.exists()` is False. | 329-351 | LLM call succeeds but output file write fails (disk full, permissions error on prompts dir). The generated section content is silently discarded. | Use `content` directly instead of re-reading from file, or at minimum log when `content` is non-empty but `output_file` does not exist. |
| 3 | task_206_prd_validation.py | D-3 Type handling | MEDIUM | `extract_json()` returns a `str`, but `validate_content()` at line 325 checks `if isinstance(content, dict)` on the return value. `extract_json` always returns a string (it extracts text from code fences), so this branch is dead code -- `content` will never be a `dict` here. The code still works because it falls through to `json.loads(content)` at line 329, but the dead isinstance check suggests a past refactor left stale logic that could confuse future maintainers into thinking dict returns are possible. | 321-326 | No runtime failure, but dead code path indicates a logic misunderstanding. If `extract_json` were ever changed to return parsed JSON, the downstream `json.loads` would crash on a dict. | Remove the `isinstance(content, dict)` branch since `extract_json` always returns `str`, or change `extract_json` to return parsed JSON and adjust callers. |
| 4 | task_206b_prd_revision.py | E-4 Data loss on normalization | MEDIUM | `apply_edit_blocks()` fuzzy fallback (lines 252-263) normalizes whitespace by stripping trailing whitespace per line, then performs the replacement on the normalized content. The result is the entire `content` variable gets its trailing whitespace stripped on ALL lines, not just the matched region. This means if only one edit block triggers the fuzzy fallback, every line in the section loses its trailing whitespace. For markdown content, trailing double-spaces (used for line breaks) would be silently removed throughout the section. | 252-263 | A PRD section uses markdown trailing-double-space line breaks. One edit block doesn't match exactly (e.g., trailing space difference). The fuzzy fallback normalizes the ENTIRE section, stripping all trailing spaces, breaking all markdown line breaks in that section. | Apply the normalized replacement only to the matched region, not the entire content. Or normalize only the search region and map the position back to the original content. |
| 5 | task_207_prd_approval.py | F-2 Unbounded loop | MEDIUM | The review loop at line 76 has `max_refinements = 3` and `max_total_iterations = 50`, but only `refine` and `custom` choices increment these counters. The `view` and invalid choices do NOT increment either counter (by design for `view`, but also for invalid choices). An infinite input loop is not possible since each iteration requires user input, but the `max_total_iterations = 50` guard is misleadingly high -- it would take 50 refine/custom cycles to trigger, while `max_refinements = 3` would trigger first. The real issue: after exhausting `max_refinements` (3 refine/custom actions), the loop exits and auto-approves at line 161 WITHOUT telling the user their PRD was auto-approved. The message says "Maximum refinement iterations reached - proceeding with approval" but this also happens when the user did 2 custom + 1 refine, which may not be what they expected. | 76, 155-162 | User does 1 custom request + 2 refine passes (not all successful). Loop exits and auto-approves the PRD at line 161 with `approver="auto-approved"`. User expected to continue reviewing but the PRD is silently approved. | Either increase `max_refinements` or ask for explicit approval confirmation before auto-approving. The `refinement_count` increments even when the refinement fails (no changes made), which prematurely exhausts the budget. |
| 6 | task_207_prd_approval.py | F-3 Refinement count on failure | MEDIUM | At lines 143 and 155, `refinement_count += 1` executes unconditionally after a `custom` or `refine` action, even if the revision produced no changes (e.g., `invoke_revision_agent` returned False, or `prd_revision_flow` returned False). This means failed refinement attempts consume the 3-attempt budget. After 3 failed LLM calls, the PRD gets auto-approved with `approver="auto-approved"`. | 137-155 | LLM provider is intermittently failing. User tries `refine` 3 times, each fails. The loop exhausts `max_refinements` and auto-approves the PRD despite no successful refinement. | Only increment `refinement_count` when the revision actually succeeded (when `revised` is True). |
