| 1 | orchestrator04.py | A-2: Default path logic | MEDIUM | `OUTPUT_DIR` default uses `ATOMIC_ROOT.parent / '.outputs' / '4-specification'` but `ATOMIC_ROOT` defaults to `Path.cwd()` when `ATOMIC_ROOT` env var is unset. If `cwd()` is the project root (not atomic-claude subdir), `ATOMIC_ROOT.parent` ascends one level above the project, placing `.outputs/` outside the project tree. Other orchestrators have the same pattern, but this is the audited scope. | 40-41 | Run `python phases/phase04/orchestrator04.py` from the project root without `ATOMIC_ROOT` set. `OUTPUT_DIR` resolves to `../. outputs/4-specification` relative to cwd. | Guard with a check that `ATOMIC_ROOT` actually contains expected markers (e.g., `core/` dir) or raise early if env var is unset and `cwd()` does not look like the atomic-claude root. |
| 2 | task_401_entry_initialization.py | E-1: Unguarded variable use after conditional | MEDIUM | `tasks_data` is set to `None` at line 71 and only assigned inside the `if tasks_file.exists()` + `try` block (line 91). If the file exists but JSON parsing fails, `tasks_data` stays `None`. The code then proceeds past the `if not verification_passed` guard (line 119) because `verification_passed` is set to `False` on parse failure (line 100), so the function returns `False`. However, if the JSON parses successfully but `task_count` is 0, `verification_passed` becomes `False` (line 97) and returns `False` at line 124. The actual risk: if `tasks_file` does not exist, `verification_passed = False` and function returns early. **No actual crash path found** — the guard at line 119 catches all failure cases before `tasks_data` is used at line 133. | 71, 91, 133 | N/A — guard is sufficient. | *Retracted after deeper analysis.* |
| 3 | task_403_openspec_generation.py | F-3: Thread safety of shared mutable state | MEDIUM | `_spec_worker` writes LLM output via `invoke_llm(output_file=...)` to `openspec_dir / f"spec-t{task_id}.json"`. Each task writes to a unique file, so no data race on files. However, `invoke_llm` internally calls `_get_default_router()` which lazily initializes a module-level singleton (`_default_router`). The code includes a warmup call at line 443 to force initialization on the main thread, but the warmup is wrapped in a `try/except` that logs a warning and continues (line 444-445). If the warmup fails (e.g., no API key, network timeout), the parallel workers will race to initialize the singleton concurrently. | 441-445, 364 | LLM warmup call fails (network error, invalid API key), then 5 threads simultaneously call `_get_default_router()` for the first time. | Make the warmup failure fatal for the parallel path, or add a thread lock around `_get_default_router()` initialization. Currently, if warmup fails, workers likely all fail individually with the same error (graceful degradation to stubs), so practical impact is low. |
| 4 | task_404_tdd_subtask_injection.py | H-2: Greedy regex for JSON extraction | MEDIUM | `_load_openspec` line 113 uses `re.search(r'\{[\s\S]*\}', content)` as a last-resort JSON extractor. The `[\s\S]*` is greedy and matches from the first `{` to the last `}` in the entire file content. If the LLM response contains multiple JSON objects or prose with braces, this captures everything between the outermost braces, producing invalid JSON. The `json.loads()` call on line 114 will then raise `JSONDecodeError`, which is caught by the outer `except` at line 116, returning `None`. This causes the task to fall back to generic subtasks silently. | 112-114 | LLM writes a spec file containing explanatory text like `The config { ... } is used` followed by the actual JSON spec. The greedy regex matches from the first `{` in prose to the closing `}` of the JSON spec, producing unparsable content. | Use a non-greedy pattern or try `json.JSONDecoder().raw_decode()` starting from each `{` (as done in `_parse_tdd_response`). |
| 5 | task_404_tdd_subtask_injection.py | D-3: Bare BaseException catch | MEDIUM | Line 560 catches `BaseException` which includes `KeyboardInterrupt` and `SystemExit`. While the intent is to clean up the temp file on any failure during atomic write, catching `BaseException` means a `KeyboardInterrupt` during `os.replace()` will trigger cleanup and then re-raise, which is correct behavior. However, the `os.unlink(tmp_path)` at line 562 could itself fail (e.g., file locked on Windows), masking the original exception with an `OSError`. | 560-563 | User presses Ctrl+C during `json.dumps` (line 558). `BaseException` is caught, `os.unlink` is attempted. On Windows, if the temp file handle is not fully released, `os.unlink` raises `PermissionError`, which replaces the `KeyboardInterrupt` in the traceback. | Wrap the `os.unlink` in its own `try/except` to avoid masking the original exception: `try: os.unlink(tmp_path) except OSError: pass`. |
| 6 | task_406_closeout.py | G-1: `relative_to` can raise ValueError | MEDIUM | Line 374 calls `specs_dir.relative_to(project_root)`. If `specs_dir` was reassigned to the legacy path `.claude/specs/` (line 315) and `project_root` is the expected parent, this works. However, if `specs_dir` is on a different drive or resolved differently (e.g., symlinks, UNC paths on Windows), `relative_to()` raises `ValueError: path is not relative to other path`. Same issue at line 425. | 374, 425 | On Windows, `atomic_root` is on drive `W:` but a symlink in `.openspec` points to a path on `C:`. `specs_dir` resolves to `C:\...` while `project_root` is `W:\...`. `relative_to()` raises `ValueError`. | Use `try/except ValueError` around `relative_to()` calls, or use `os.path.relpath()` which handles cross-drive gracefully (returns absolute path). |
