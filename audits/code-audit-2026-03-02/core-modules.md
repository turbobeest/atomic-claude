## Summary

**Files audited**: 17
**Findings**: 10 total (0 CRITICAL, 2 HIGH, 8 MEDIUM)

### By severity
- **CRITICAL**: 0
- **HIGH**: 2 (Cypher injection in reader.py filter keys and relationship types)
- **MEDIUM**: 8 (label injection, Windows file locking, command injection defaults, config path traversal, SSRF TOCTOU)

### Key themes

1. **Cypher injection in graph/reader.py (HIGH)**: The writer module has comprehensive input validation (`_validate_property_key`, `_validate_label`, `validate_relationship`), but the reader module interpolates filter keys, labels, and relationship types directly into Cypher queries without any validation. This is the most significant finding -- the writer's security model is not consistently applied to read operations.

2. **Windows file locking edge cases (MEDIUM)**: Both `state.py` and `llm/invoke.py` use `msvcrt.locking()` on Windows with byte ranges that may not align with actual file sizes, potentially causing lock acquisition failures that degrade to unlocked operation.

3. **Defense-in-depth gaps in subprocess_runner.py (MEDIUM)**: The `run_bash_command()` function defaults to allowing shell metacharacters, relying entirely on caller discipline for safety. The opt-in `reject_shell_meta` flag should be opt-out instead.

4. **Parent directory config loading (MEDIUM)**: Both `config.py` and `resolver.py` load configuration from `atomic_root.parent/.outputs/`, which means config integrity depends on the security of the parent directory rather than the project directory itself.
